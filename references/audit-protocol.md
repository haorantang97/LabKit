# Open Loops 审查协议

每次业务审查前完整读取本文件。不要凭记忆执行。

## 目录

1. 输入与顺序
2. 两个方向的闭环
3. 建立回应层级
4. 回应义务门槛
5. 映射用户回应
6. 代决与岔路
7. 核销旧条目
8. 登记与输出

## 1. 输入与顺序

只读取：

1. `docs/open-loops-source.md` 最后两段：上一轮用户与助手、本轮用户。
2. `docs/open-loops.md` 当前全部未闭环。

严格按顺序执行：

1. 核销和修正全部旧条目。
2. 提取用户上一轮的明确请求。
3. 为助手上一轮回答建立层级。
4. 只在主层级生成候选回应单元。
5. 映射用户本轮回应。
6. 独立扫描代决和岔路，再校验证据。
7. 去重后写卡并更新轮次。

不要依赖主 agent 转述，不判断回答质量，不修改原文存档。

## 2. 两个方向的闭环

### A. 用户 → 助手：请求缺口

用户提出的问题、任务或交付要求没有被助手看见或完整回答时登记。先区分两种请求：

- **执行型请求**：用户要求删除、修改、开发、提交等动作。助手明确点名该动作并承诺承接，就表示信息
  已被看见；是否最终做完交给任务管理，不继续作为请求缺口。只说“会处理这些”但没有指向该动作不算。
- **回答型请求**：用户要求解释、调研、比较、方案、判断或内容交付。必须实际提供所要内容；只承诺稍后
  回答不能关闭。

关闭请求缺口必须匹配原要求的：

- 数量：要求“三个方案”，只给一个不能关闭。
- 范围：要求 CRM 和 ERP，只答 CRM 不能关闭。
- 形式：要求调研、比较、实现或文件，不能用“以后会做”代替。
- 限定：用户明确要求真实数据、权限边界或不使用模拟数据时必须覆盖。

“方案、解法、交互方式”必须给出用户可以评价的机制、结构或选项。重复目标、换一个形容词，或只说
“让它更清楚”“名称和用途更明确”，不算交付交互解法。

执行型请求被明确承接，或回答型请求后来完整交付后，请求缺口立即移入已闭环，不要求用户再回复
“收到”。回答型请求只完成部分时保留，并更新缺口理由。

### B. 助手 → 用户：回应缺口

助手产生需要用户回应的主结论、建议、执行点、风险、选择、限定或知识点，而用户只接住同组一部分时，
登记遗漏的同级单元。

不要把 A 和 B 混成一条。一个用户请求可以因答案交付而关闭；答案中新增的独立回应单元仍可另行审查。

描述性知识默认不因用户完全沉默而全部登记。只有以下情况之一成立才形成回应缺口：

- 用户本轮已经回应同一显式分组中的部分知识点，遗漏了兄弟项。
- 助手明确要求用户确认该结论或限定。

重大风险、限定或不确定性若只是回答用户要求的调研或解释，也遵守上面两条，不能仅因“很重要”自动
转成回应缺口。只有它被单独提出为当前行动的待确认约束、选择或例外时，才作为行动类主单元审查。

这样既覆盖非执行场景的局部遗漏，也避免把每次知识回答变成“等待收到”的清单。

## 3. 建立回应层级

先把助手回答划分为：

```text
主方案 / 主结论 / 最终建议
├── 普通组成部分
├── 支撑理由
├── 示例、证据与链接
└── 需要单独确认的重大例外或选择
```

### 主层级选择顺序

1. 回答最末尾明确标记的整体“建议、结论、下一步”清单或组合句。
2. 用户明确要求比较的并列方案或编号知识点。
3. 没有总结时，标题级方案、结论或自然段中的顶层主张。

最末尾的整体建议会遮蔽前文语义重复的编号建议、表格、解释和技术展开。只审最后的整体范围；如果它
把前文多项合成一个自然的下一步组合，就把组合视为一个父项，不再逐条审前文组成。

### 粒度规则

- 一句自然的用户回复可以共同接受、拒绝或质疑的内容，合并为一个单元。
- 同一方案下的图表行、字段、步骤和实现细节默认是子项，不逐行登记。
- 表格只有在每一行都被明确提供为可独立选择的方案时，才按行形成同级单元。
- 一个编号项内部的并列组成通常仍是一个单元；不要把“库存、订单、逾期接口”拆成三条。
- 禁止同一轮同时登记父项和普通子项。

### 父子覆盖

- 用户明确接住父项，默认覆盖其普通组成、支撑理由和实现细节。
- 重大例外、独立风险或另一个明确选择不会被父项自动覆盖。
- 用户只接住子项，不能自动覆盖父项或其他兄弟项。

## 4. 回应义务门槛

候选内容必须同时满足：

1. 它处于主层级，或是必须单独确认的重大例外。
2. 它承载独立的行动、意义、判断、选择或边界。
3. 不回应会留下尚未确认的理解、行动、选择、风险或责任。
4. 它没有被已接住的父项覆盖。

可以包括执行点、建议点、知识点、判断、限定、不确定性、风险、选择和待确认假设；列表不是穷举。
研究、学习、咨询、分析、诊断、决策、编码、写作、创意等场景使用同一门槛。

绝对不登记：

- 纯例子、引用、链接、证据来源和同义复述。
- 已完成工作的状态汇报、测试数字和打开方式。
- 用户已经授权范围内的实现顺序、代码复用、组件组织、调试方式和草稿 PR 等机械细节。
- 为已授权目标选择的内部实现手段，例如 WebSocket 通知后重拉、轮询间隔、API 形状、缓存、队列和
  组件拆分；除非用户明确要求比较或选择这项架构。
- 已被父项覆盖的普通子项。
- 只因“删掉会少信息”但并不需要用户回应的背景说明。

不要用删除测试单独决定登记；删除测试只能辅助判断信息是否实质，不能证明它有回应义务。

## 5. 映射用户回应

“接住”包括接受、反对、质疑、纠正、搁置、转知识库/项目卡片，或无歧义的整组确认。

- 用户点名某项，只覆盖该项和它的普通子项。
- “以上五条全部同意”覆盖明确的五项整组。
- “继续”只在它紧接助手明确提出的下一步组合、且没有其他合理指向时覆盖该组合。
- 只回应第 1、4、5 项，不能覆盖第 2、3 项。
- 对父项的接受覆盖普通子项；对子项的回应不覆盖兄弟项。
- 用户明确接住后立即出表；做不做、什么时候做不归本清单。

## 6. 代决与岔路

### 代决

代决扫描独立于回应层级和用户是否回应同组兄弟项。逐句查找“我先按 X 理解”“我先锁定 X”
“默认采用 X”“我选择 X”以及已经实际采用某方向的表达；它们不能被普通父项或最终总结遮蔽。

只有同时满足以下条件才登记：

1. 助手明确选择、宣布默认或实际采用了一个方向；不要求已经完成实现。
2. 该选择会改变产品行为、语义、权限、数据范围、成本、外部影响、范围或不可逆结果。
3. 替代方向能从本轮原文直接引用：用户提出过、助手列出过，或原文同时出现 X 与“不是 Y”。
4. 用户没有明确授权或接住该选择。

登记时必须能写出：`选择 X（替代项 Y；原文证据：……）`。

X 与 Y 必须引用构成分歧的最小互斥片段。解释单个词时，Y 只抄原词或另一种词义；禁止把同一句里的
用途、背景、理由或其他要求拼进替代项。一个代决只表达一道选择题。

禁止审查员自行发明 Y。找不到替代项原文就不得登记为代决。用户已经明确要求的方向，以及授权范围内的
代码复用、实现结构、测试、提交、推送、启动和调试，不是代决。
为用户已经要求的目标选择 WebSocket、轮询、缓存、队列或内部接口，也不是代决；用户明确把这些架构
作为选择题时例外。

替代项必须是用户仍可能选择的真实分支，不能只是用户已经明确要求删除、改变或改善的旧状态。例如用户
已经说当前入口不明确并要求更好的交互，“继续保留不明确的旧入口”不是合法替代项；助手提出让入口更
明确属于回答该请求，不再重复登记为代决。若助手收窄、改变或曲解了用户原要求，仍按真实代决处理。

原文证据可以跨同一轮的用户与助手消息配对，例如用户写“案件”、助手说“先按按键理解”；用户要求把
界面改成橄榄绿、助手明确收窄为“只承担选中和重点数据，不把整屏刷绿”。这两类语义解释和视觉范围
都会改变产品结果，用户未回应时必须登记。

### 岔路

只有不同回答会实质改变结果，而且助手本应让用户选择时才登记。必须写成用户可以直接回答的问句；
写不出问句就不登记。

## 7. 核销旧条目

逐条读取当前未闭环，只用上一轮助手与本轮用户原文判断：

- 执行型请求缺口：助手已明确点名并承接动作 → 已闭环，不等待做完。
- 回答型请求缺口：助手已按数量、范围、形式和限定完整交付 → 已闭环。
- 回答型请求缺口：只承诺或只完成部分 → 保留并把理由改成当前真实缺口。
- 代决：用户明确接住前继续挂；助手后来解释不等于用户确认。
- 回应缺口：用户接受、反对、质疑、搁置或转入别处 → 已闭环。
- 模糊的“先不管”不是废弃；写明“确认废弃吗？”继续挂。

禁止因为时间、轮数或换话题自动关闭。禁止把“讲过一些”当成完整回答。

## 8. 登记与输出

写卡前做四项校验：

1. 每条是否处于主层级？
2. 是否与父项、最终清单或现有条目重复？
3. 代决是否有替代项原文证据？
4. 用户是否已经逐项或整组接住？

第 1 项不适用于通过第 6 节独立扫描得到的真实代决；代决以四项证据门槛为准。

一条一行，抄原话，不合并真正独立的同级项，也不拆分一个编号项内部的组成部分。保持现有文件结构
和区块标题。顶栏中的轮次必须直接取自原文最后一个 `===== 第 N 轮 · 用户 =====` 的 N；禁止估算、
沿用旧轮次或使用助手轮次。即使没有新增，业务轮次也推进。

未闭环条目只允许这一种 Markdown 格式：

```text
1. 「原文摘录」：为什么还挂着
2. 「原文摘录」：为什么还挂着
```

必须使用阿拉伯数字有序列表。禁止使用 `-` 项目符号、`#1`、`[回应缺口]`、状态标签或重复编号。
保留现有未闭环条目的原编号；新增项从当前最大编号继续。空卡从 `1.` 开始。

完成状态卡更新后始终向主 agent 输出 `NONE`。不得在回报中罗列新增项、全表、历史积压、已闭环或
“本轮无变化”。新增遗漏只进入状态卡。

对话窗口的积压阈值提醒由主 agent 根据审查前后的未闭环总数处理，审查员不得自行提醒、计算越线或
输出 `⚠`。这样可以避免新增项逐条刷屏，并确保持续高于阈值时不会重复提醒。
